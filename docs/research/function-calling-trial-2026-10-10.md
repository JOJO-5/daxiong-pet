# 第二轮：原生 function calling 实测

日期：2026-10-10（北京时间）。承接用户对第一轮“提示式 JSON 不等于原生函数调用”的提醒，本轮实际使用原生 `tools` / `tool_choice` API。

## 结论

**小模型能做原生函数调用，不能用第一轮 JSON 失败把这条路线排除。** 三个候选都返回过标准 `message.tool_calls`。约219MB 的 LFM QAD 直接工具配置在6个游戏正例和4个游戏相关不调用场景中全部正确；Qwen 加示例后严格通过21/24；普通LFM Q4_K_M还发现了需要修复的历史模板兼容问题。

同时，**原生调用不等于允许直接写长期记忆**：QAD直接工具组误调用2次；Qwen示例组误调用1次；修复后的Q4_K_M示例组在本次12个反例中无误调用，却漏掉5个偏好请求。小样本未出现错误不能宣称普遍可靠。当前结论是保留小模型工具路线、继续拆任务与做主程序校验；不是已确定默认模型或完成AI接入。

本轮 **144个主判分请求 +24个模板修复补测 =168个判分请求**，另5个成功提案的模拟工具回传续答。所有数据合成；没有真实数据库写入、游戏执行、截图或外部大模型调用。

## 怎么测

运行器、三个权重的revision/SHA-256与[第一轮](ai-cpu-trial-2026-10-10.md)相同；运行前重新校验。Linux共享云，Xeon Platinum 8573C，2核CPU配额、8GiB cgroup内存，CPU两线程、GPU layers=0。4096上下文、最多160输出token、单并发、temperature=0.1、top_k=50、top_p=1、min_p=0、repeat_penalty=1.05、seed=20261010、关闭thinking。

工具：

- `remember_preference(key, value)`：称呼或说话方式，key仅user_name/speech_preference。
- `play_game(game)`：ball/frisbee/tug，工具定义明确中英文映射。
- `stop_game()`：停止游戏。

使用 `tool_choice=auto`，允许模型不调用；没有用required强迫反例调用。`parallel_tool_calls=false`。只认API的`message.tool_calls`，正文中写JSON/XML不计为调用；不eval模型文本。检查函数白名单、字段、枚举和非空字符串，再做期望语义比对。**这里的校验是评测用检查，不是已经实现的偏好来源授权器。**

每组24个新实例，12个应调用、12个不应调用，没有重复计分：新称呼、说话方式、旧偏好更新、球/盘/拔河/停止，以及第三方、引用、假设、否定、临时状态、聊天和屏幕文字。偏好只测试称呼/说话方式，不代表所有个人偏好。两组分别无示例与带固定正/反例、模拟tool-role回传；示例没有根据24条结果优化，但含“格式示例/未执行”措辞，可能影响判断，不宣称最优提示。

允许相同提示前缀缓存，实际命中保留在usage；只复用计算，不继承未提供的对话。本轮提示、工具、数据、参数、上下文和缓存策略都与第一轮不同，因此 **不是“只改变function calling”的受控对照，也不能直接比较两轮百分比或延迟**。

168个判分请求均无HTTP异常、无参数结构校验失败、无160-token输出截断。但结构合法并不代表内容正确；无调用也可能输出不实承诺。上述时延是完整响应，含工具提示计算和生成，包含每组首请求，并非首字。缓存命中和提示长度不一样，不能用来宣布某模型/量化必然更快。本轮没重新测内存/游戏并行，不沿用第一轮峰值当4096上下文的实测。

具体失败：

- QAD直接组 `friend_name`：把朋友希望被叫阿禾，调用为主人的user_name=阿禾；`negative_name`：对“我没有要求你以后叫我小夏”仍写入小夏。这两次调用结构完全合法。
- QAD直接组新称呼2/2、游戏6/6，但说话偏好0/2、偏好更新0/2；有些只是口头“好的，禾禾”，未提出工具调用。
- Qwen直接组有正文 `<remember_preference key="user_name" value="小夏">`，不是API调用；示例组 `speech_1` 正文写出了JSON，仍未调用。
- Qwen示例组 `hypothetical_name` 对假设里的禾禾发起记忆调用，且key错成speech_preference。
- Qwen示例组 `speech_2` 返回原生调用，value=“温柔”，期望“温柔一点”；这是语义近似但严格措辞不匹配，**21/24不是纯语义准确率**，该条不能与误记他人混为一谈。

## 找到并修复历史模板问题

两个LFM GGUF的内置模板并不相同。Q4_K_M的`chat_template_caps.supports_tool_calls=false`，但运行器专用解析器仍可识别新生成的原生调用，所以不能只看caps就说完全不支持。

实际 `/apply-template` 展开后发现：Q4_K_M的两条assistant示例调用被渲染成空内容，函数名与参数均丢失。该组0/12正例说明原配置有问题，**不能作为有效few-shot能力评测或归因于量化精度**。QAD模板与Qwen模板保留了历史调用。

补测用同一固定官方仓库QAD GGUF提供的完整LFM模板，通过`--chat-template-file`覆盖Q4_K_M模板，未修改权重。先确认历史中出现`<|tool_call_start|>[remember_preference(...)]`，再复测同24个实例。结果从原模板12/24到19/24，正例从0/12到7/12；游戏6/6，反例12/12。更换的是完整模板，不把改善全部归于一行，也没有在新独立测试集上验证。

模板保存在[lfm-history-template.jinja](../../scripts/ai-prototype/lfm-history-template.jinja)，来源、SHA-256及第三方许可证见[NOTICE](../../scripts/ai-prototype/NOTICE.md)。LFM仍是自有许可证，不因模板可修复就变成Apache。原始失败与补测均保留，不替换旧结果。

## 工具回传与下一步

共5次模拟续答（QAD飞盘、Qwen称呼/飞盘、修复Q4_K_M称呼/飞盘）均接受tool-role响应且没有HTTP异常。回传明确`executed=false`。QAD及修复Q4_K_M能说明原型未执行；Qwen称呼续答“好的，我叫阿禾”仍混淆主人与宠物的名字。**协议流程通过不等于自然语言正确，更不等于SQLite或游戏已接入。**

下一轮优先：

1. 将称呼与说话方式拆成专用工具，减少key选择混淆；缩减单请求工具集合，避免一个模型包办所有任务。
2. 在主程序侧验证偏好来自本人明确声明；覆盖否定、引用、第三人称、假设、来源和更新冲突。不要只靠字段schema决定写库，不确定时不保存，保留撤销。
3. 固定兼容模板，改用自然、清晰的正反例及工具结果，再用新的、更多样的测试集检验误调用和漏调用。对语义近似值另外做审查，不能看过结果后改golden抬分。
4. 有限游戏命令优先确定性解析；原生工具作为更多自然表达的候选。聊天与工具任务分别选配置，暂不因为本轮函数调用成绩选定默认中文聊天模型。
