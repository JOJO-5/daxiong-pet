# 面向手机的小模型与大熊安装包体积调研

日期：2026-10-10（北京时间）。本次读取官方模型卡、许可证、运行器文档及 Hugging Face 文件元数据，没有下载权重、运行推理或测量安装包。下面的 MB 为十进制文件大小，不能当作内存或安装包压缩后的大小。

本次需求调整：默认安装包内置可用的小语言模型和运行器，同时允许接入用户选择的大模型服务；尽量降低包大小。调研手机/边缘设备模型是为了改善桌面项目的体积与 CPU 体验，不代表本阶段要开发 Android/iOS 宠物应用。

## 后续实测更新

已按用户要求实际下载并完成三个候选纯 CPU 首测，见[2026-10-10 CPU 实测报告](ai-cpu-trial-2026-10-10.md)。两版 LFM 在本轮中文聊天/偏好任务上未达标，不再凭体积优先建议其为默认聊天；Qwen 中文相对较好，但同样未通过自动记忆/约束要求，且明显超过250MB权重目标。下文保留前期元数据调研和当时的候选排序，最终决策以实测及后续复验为准。

## 建议结论（首测前）

优先评测 **LFM2.5-350M 的官方 QAD Q4_0（219.31MB）与 Q4_K_M（229.31MB）**，以 **Qwen3-0.6B Q4_K_M（484.22MB）** 作中文质量与 Apache-2.0 许可证对照。前者是当前查到的较有希望兼顾中文、端侧运行和小体积的候选，但其 LFM Open License 有商业使用门槛，不能按 Apache/MIT 处理，也不能仅凭模型卡把中文陪伴质量认定为合格。

默认包只带一个纯文字模型；轻量 OCR 单独核算。更大的图像模型/视觉组件、2B 质量档、GPU 专用运行库作为可选增强，不默认打进所有包。允许用户外接大模型提升质量，但基础离线聊天必须仍然可用。

建议第一轮优化目标：默认内置语言权重 <=250MB，AI 增量资源（权重、CPU 运行器及必要辅助文件）争取 <=300MB。这是待测目标，不是已实现体积；中文质量或可再分发条件不满足时，报告取舍，不能为了体积强行选失效的小模型。OCR 若内置，其运行库与字典也必须计入增量预算。

## 2. 手机模型为什么不一定适合直接内置

### LFM2.5-350M

官方说明支持端侧部署和 llama.cpp，并列出中文等语言，推荐用于数据提取、结构化输出和工具调用；不推荐知识密集任务与编程。这适合评测偏好提取、已有动作意图和宠物短句，不能据此承诺复杂聊天能力。

其官方展示的手机/AMD CPU 吞吐和“低于 1GB”内存属于发布者特定测试，不是大熊的实际成绩；本项目仍须固定 CPU、线程、上下文、量化、输入长度测首句延迟与进程树内存。

许可证为 **LFM Open License v1.0**：所读取条款的商业使用门槛为年收入达到或超过 1,000 万美元，超过门槛的商业使用不在该许可证授权范围内。再分发需携带许可证、保留相应通知等。若项目要提供不受此门槛影响的默认分发，优先选择 Apache-2.0 的 Qwen 对照，或另行取得合适授权；不能改项目许可证就消除模型条款。

来源：[官方模型卡](https://huggingface.co/LiquidAI/LFM2.5-350M)、[官方 GGUF 与 QAD 说明](https://huggingface.co/LiquidAI/LFM2.5-350M-GGUF)、[本次固定 revision 的许可证](https://huggingface.co/LiquidAI/LFM2.5-350M-GGUF/blob/657e078c94084481950a2d555a941481f715536b/LICENSE)。

### Gemma 3 270M / Gemma 3n

Gemma 3 270M 是可面向移动设备的小文字模型；选定社区 Q4 文件约 253MB。Google 的家族级多语言描述和更大型号基准不能替代这个 270M 的中文体验测试。Gemma 条款不是 Apache-2.0，原始权重有条款接受流程；本次没有访问受限原始文件或把访问失败解释为模型不存在。

**Gemma 3n E2B 面向手机，但不适合作为缩小包的首选。** 官方说明 E2B 是有效参数规模，实际总参数约 5B，PLE 缓存等优化降低运行内存；“约 2GB 内存运行”不意味着下载文件只有 2GB，更不意味着比 350M 权重小。未核定本项目实际量化文件体积，不用有效参数数乘 4-bit 推算安装包。

来源：[Gemma 3 模型卡](https://ai.google.dev/gemma/docs/core/model_card_3)、[型号与设备用途](https://ai.google.dev/gemma/docs/get_started)、[Gemma 3n 机制](https://ai.google.dev/gemma/docs/gemma-3n)、[Google 端侧说明](https://developers.googleblog.com/en/introducing-gemma-3n-developer-guide/)、[Gemma 条款](https://ai.google.dev/gemma/terms)。

### SmolLM2 / MobileLLM / OpenELM

- **SmolLM2 135M/360M**：确实很小，可端侧运行，Apache-2.0；官方语言标签与限制主要针对英语。用一个英语模型强行维持中文性格，可能省体积却失去目标体验。先作对照，不承诺微调少量语料即可补足中文。
- **Meta MobileLLM 125M/350M**：官方针对亚十亿参数端侧模型研究，仓库当前标注 FAIR 非商业许可证，不能当普通宽松商业可分发模型。原始型号不等于已适配的中文聊天指令模型。本次未取得可核实的目标 GGUF 文件体积，不以参数估算冒充文件数据。
- **Apple OpenELM 270M**：官方提供小型指令模型与研究框架，语言训练来源主要是英语语料集合，使用自有许可；还涉及 tokenizer 与跨平台运行器支持。没有理由因为是 Apple 发布就认定 Mac/Windows 中文陪伴可直接使用。本次未核定对应量化包，不纳入默认优先。

来源：[SmolLM2 135M](https://huggingface.co/HuggingFaceTB/SmolLM2-135M-Instruct)、[360M](https://huggingface.co/HuggingFaceTB/SmolLM2-360M-Instruct)、[MobileLLM 官方仓库](https://github.com/facebookresearch/MobileLLM)、[OpenELM 官方模型卡](https://huggingface.co/apple/OpenELM-270M-Instruct)。

### 手机系统自带模型和运行器

Android Gemini Nano 通过 AICore/设备及 API 能力提供，不是一个能随本项目跨平台安装包再分发的通用权重。Google AI Edge LiteRT-LM 可以作为未来手机端运行器的评测对象；手机可用不代表现有 Windows/macOS/Linux 三平台已经验证。

当前桌面首选仍是裁剪后的 llama.cpp CPU 运行器；未来真正开发手机应用时，再评估 Android NDK/llama.cpp 或 LiteRT-LM、iOS 的对应运行路线，不把所有移动运行器塞进桌面包。

来源：[Android Gemini Nano](https://developer.android.com/ai/gemini-nano)、[LiteRT-LM](https://developers.google.com/edge/litert-lm)、[llama.cpp Android 文档](https://github.com/ggml-org/llama.cpp/blob/master/docs/android.md)。

## 3. 降低包大小的具体做法

1. 默认包只带一个选定量化语言模型，不带 FP16 原始模型、重复转换文件、训练数据或开发框架。
2. CPU 运行器按 Windows/macOS 两架构/Linux 分别打包；排除测试程序、调试符号和不使用的后端依赖，但保留实际运行所需的共享库、许可证及通知。
3. 不把 Ollama、LM Studio、Python/PyTorch 整套产品内置；外接它们的已有本地服务只需要适配协议。
4. 视觉模型和更大语言模型提供可选增强包；默认识字方案若内置 OCR，把模型、字典、预处理和 ONNX Runtime 一起核算，不只报模型数 MB。
5. GPU CUDA 等体积较大的依赖不默认全厂商捆绑；优先 CPU，后续可选平台后端。Vulkan/Metal 也要测真实依赖成本。
6. 优先比较常规 4-bit 与量化感知方案；2-bit/3-bit 仅作为有同一套中文质量结果的实验，不为了几 MB 牺牲角色或记忆准确性。
7. GGUF 量化文件仍可能含较高精度张量及 tokenizer 元数据，不能用参数数 × 位宽代替真实字节数。
8. 安装包压缩能节省多少须构建后实测；已量化权重不承诺再压缩一半，也不把缩短上下文当作缩小磁盘权重的方法。
9. 更新时避免重复下载/保存相同哈希的模型；支持已有权重复用，研究差量更新但不预先承诺对量化文件有显著收益。
10. 默认完整包满足开箱即用；可另提供无模型的轻量包，但不能悄悄把默认包改成首次启动还必须联网下载的方案。

记录四类大小：各平台下载包、安装后占用、模型单文件、实际运行峰值内存。推荐报告“AI 增量”并与同平台无 AI 基线对照，避免用 Windows 包大小代表 Linux AppImage。

## 4. 内置与外接模型的执行约束

- 界面允许分别选择聊天后端与屏幕理解后端：内置、本地服务、远程服务。
- 外接优先实现 OpenAI 风格 Chat Completions 适配；本地 Ollama 原生接口及兼容接口、LM Studio 的本地接口按实际功能测试。
- 用户配置 base URL、模型名和凭据，提供连接测试、取消、超时与可读错误。不能把“OpenAI-compatible”当所有供应商图片输入、JSON、工具调用和流式响应完全一致。
- 建立能力表：文字、图片、流式、工具/结构化输出、上下文限额。缺少能力时准确提示或走明确配置的回退，不伪造已看图。
- API Key 存系统安全凭据设施；SQLite 保存非敏感设置/凭据引用，日志不打印 Key。
- 云端聊天开通不代表屏幕可以发送云端。屏幕截图、OCR、摘要发送远程要有独立明确开关；只发本次必要内容，保持屏幕上下文短期。
- 外接失败时，可以回退内置语言短句，但不得将用户原本选择本地处理的数据悄悄改发另一家云端。
- SQLite 30 天聊天、明确偏好自动记忆、GUI 性格和独立观察/发言计时保持不变。

## 5. 下一轮必须补的真实评测

首轮比较：LFM2.5-350M QAD Q4_0、同模型 Q4_K_M、Qwen3-0.6B Q4_K_M；Gemma/SmolLM 作为次要对照。需要默认不受 LFM 商业门槛影响时，Qwen 提升为优先路线。

同样的 100 条中文聊天/性格/偏好样本、相同短上下文和 CPU 线程预算，评测自然度、重复、胡编、错误记忆和动作输出；结构化能力不能替代陪伴质量。模型推荐采样参数可各自采用并记录，不为凑公平强迫所有架构使用相同温度。

测冷/热启动、首句、完整回复、进程树内存、卸载释放，及推理时真实拖动、球/盘、气泡是否卡顿；同时构建四平台试验包测实际 AI 增量大小。无设备的项写未验证。

只有中文质量、运行兼容、包体积、再分发条件四项一起通过，才决定内置型号。当前成果是可追溯的候选与尺寸调查，不是已经选定/内置了 219MB 模型。
