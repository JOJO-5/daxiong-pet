# 后续 AI 接入选型

2026-10-11（北京时间）。用户要求先选型，再进行后续接入。本次确定开发基线，不把元数据、下载成功或平台包存在写成推理/性能验收通过。

## 选型结论

| 部件 | 开发基线 | 选择理由与边界 |
| --- | --- | --- |
| 聊天/画面理解 | 现有 Qwen3.5-2B Q4_K_M + 同 revision 的 BF16 mmproj，沿用 llama.cpp CPU | 复用已发布文字模型；只增加配套视觉组件，无须再装第二个语言模型。2B 图片推理尚未验证。 |
| OCR | PP-OCRv5 mobile 中文检测 + 中文识别 ONNX | 下载核验后两文件合计 21,450,882 字节。先保留中文识别基线，再用更小候选比较，尚不能声称准确率领先。 |
| OCR 对照 | PP-OCRv6 tiny 检测 + 识别 | 合计 6,319,431 字节，约省 15.13MB；未测试中文办公小字，暂不据体积直接替换。 |
| OCR 运行器 | ONNX Runtime CPU，1.23.2 为四平台原型基线 | 官方该版有 Windows x64、Linux x64、macOS ARM64、macOS x86_64 资产；不带 CUDA/显卡专用依赖。发布前检查该版本问题及更新路径。 |
| OCR 产品接入 | 独立原生 worker，Rust 调用 ONNX Runtime；RapidOCR 3.10.0 用作 Python 对照原型 | 正式安装包不要求安装 Python，不把 Python/OpenCV 整套环境装入产品。复用对应预处理/后处理的行为规范，不假设只加载 ONNX 就能识字。 |
| 外接大模型 | OpenAI 风格 HTTP 接口 + 显式文字/图片能力探测 | 复用聊天流式、取消和错误处理；API 地址、模型名和凭据通过界面设置。图片支持依服务实测，不靠模型名字猜。 |

当前先补 OCR 与视觉验证，再接观察调度；外接模型保持独立阶段。截图实现采用平台适配层，先做前台窗口原生捕获验证，再评估 xcap（检索到稳定版 0.9.8）。尚不锁定截图库：macOS 权限/前台窗口范围、Linux Wayland/PipeWire 与 X11 差异必须先验证，不能仅凭库的跨平台说明定案。

## 下载与兼容性证据

本次四个 ONNX 文件已实际下载，SHA-256 全部与固定 RapidOCR v3.10.0 上游声明一致。[模型字节与哈希](next-ai-integration-2026-10-11/models.json)；模型保存在 Git 外，未进入源码仓库。尚未执行 OCR 推理，字典和 ONNX 元数据仍需配对核对。

[本次上游查询](next-ai-integration-2026-10-11/sources.json)返回 ONNX Runtime 最新版 v1.31.0，其发布资产中有 macOS ARM64，没有 macOS x86_64；不能据此宣称已覆盖项目四个平台。[1.23.2 CPU 包证据](next-ai-integration-2026-10-11/v1.23.2.json)包含两种 Mac 架构，故选为兼容性原型基线。运行时包压缩大小：Linux x64 8.31MB、Mac ARM64 10.00MB、Mac Intel 11.68MB、Windows x64 78.13MB；这些是完整上游归档，不能直接作为最终安装包增量。只分发所需动态库与许可证，验证 DLL/共享库依赖和原生启动。

Rust `ort` 当前版本列表首项为 2.0.0-rc.13，没有稳定版；rc.10 的构建脚本声明 ONNX Runtime 1.22.0。因此不直接混配最新绑定和旧运行库：下一步锁定支持目标 C API 的绑定，验证 1.23.2 原生加载与 session 推理后记录确切版本。必要时用隔离 C ABI 适配层，不能以自动下载行为悄悄改变运行器。

许可证查询：ONNX Runtime 为 MIT；PaddleOCR 与 RapidOCR 为 Apache-2.0。框架许可证不是转换权重/字典完整来源链的替代，分发前补齐所选权重、字典及第三方依赖归属说明。

## 包大小与性能策略

文字模型 1,270,808,032 字节，配套视觉组件 671,372,416 字节，合计 1,942,180,448 字节。加 v5 OCR 权重后为 1,963,631,330 字节，尚未包括运行器、字典、应用和许可证。这是原始文件大小；实际安装包需实测压缩，尤其检查 GitHub 单资产 2GiB 限制。优先保留内置要求，若超限采用可审查的分卷/资源分包方式，不悄悄改成联网后才能使用。

默认观察先变化检测，再 OCR，再让现有 2B 根据有限文字生成短句。用户主动问图片或需要画面关系时才启动图片模式。OCR 不能代替图片理解；视觉组件按需加载/卸载，具体是否需要重启模型 worker 以 llama.cpp 实测决定。最多一个重型任务运行，聊天优先，过期观察跳过，禁止在宠物 tick 中做识图或数据库工作。

观察频率与说话频率保持独立；默认前台窗口，可切整个桌面。截图、OCR 与画面摘要只进入有期限的内存上下文，不作为长期偏好。性格仍由已有 GUI 修改。

## 接入与验收顺序

1. 固定 OCR 字典、元数据、输入归一化、检测框缩放还原、裁剪与 CTC 解码；用 RapidOCR 显式指定 v5 mobile 做对照，其默认配置是 v6 small。
2. 合成非私人办公样本：中文 12/14/16px、代码、数字/金额、混排、低对比、图片无文字；比较 v5 与 v6 tiny 的字符错误率、检测漏字、端到端耗时、峰值内存。根据结果决定是否替换，未通过不接主动说话。
3. 四个平台运行独立 OCR worker；验证取消、超时、异常退出、空结果与模型缺失。核对原生库依赖和最低系统版本。
4. 下载固定 revision 的 2B projector，校验哈希，测试真实图片协议、短图文回答、取消、切回聊天与内存释放。此前 0.8B 试验不作为 2B 验收。
5. 授权截图与短期观察上下文接入，再做独立观察/说话调度；最后验证完整打包及原生操作。

8GB/11代 i5 的图片时延、OCR时延与内存尚未测量；本次不承诺流畅秒回。共享云机测量只作为回归对照。未改宠物形象或动画。

上游入口：[RapidOCR 3.10.0](https://github.com/RapidAI/RapidOCR/releases/tag/v3.10.0)、[ONNX Runtime 1.23.2](https://github.com/microsoft/onnxruntime/releases/tag/v1.23.2)、[ort rc.10 构建脚本](https://github.com/pykeio/ort/blob/v2.0.0-rc.10/ort-sys/build.rs)。
