# OCR CPU 首轮对比与接入基线

2026-10-11（北京时间）。完成 PP-OCRv5 mobile 与 PP-OCRv6 tiny 的真实 Linux CPU 推理，继续采用 v5 mobile 作为首个原生接入基线。v6 明显更快、更小，但本轮出现无文字图形误报和更多相似字母错误；不据这组小样本宣称 v5 在所有任务上更准，也不排除后续使用 v6。

## 方法与范围

独立虚拟环境：RapidOCR 3.10.0、ONNX Runtime 1.23.2，[完整依赖锁定](ocr-cpu-trial-2026-10-11/requirements.lock.txt)。Linux x64，共享云机 cgroup CPU 配额 `200000 100000`（最多两核 CPU 时间），intra-op 2 线程、inter-op 1 线程，两套逐个运行，没有同时跑语言模型。所有 ONNX session 实际 provider 仅 CPUExecutionProvider，没有使用 GPU。

明确指定四个已校验模型文件路径，关闭方向分类，不使用 wheel 默认内置 v6 small 模型。960×600 稀疏样本共10张：中文12/14/16px、英文代码、中英混排、金额/小数/字母数字、低对比、深色、纯白、几何图形；另有1920×1080、30行文字的亮/暗两张页面。字体为 NotoSansCJK-Regular.ttc，哈希在每份原始报告中。页面是自行生成的合成图片，不捕获用户真实屏幕。

每套每张4次，首遍单独记录，余下3次计热运行；每套48次，共96次调用。文字结果四次一致。CER 保留字符、数字、大小写和标点，**仅移除空白**，所以“代码读对”不能理解成空格/缩进也完全保留。按一次结果计分，重复次数不扩充独立质量样本数；稀疏文字422字符、两张整页2352字符。整页重复了前三句并附不同编号，不能当作丰富真实办公数据集。

## 测量结果

| 样本/指标 | v5 mobile | v6 tiny |
| --- | ---: | ---: |
| 稀疏文字 CER | 1/422（0.24%） | 3/422（0.71%） |
| 稀疏全部10张热运行中位数 | 796.85ms | 309.55ms |
| 稀疏进程峰值内存 | 357.32MiB | 258.94MiB |
| 1080p 30行两张 CER | 0/2352 | 0/2352 |
| 1080p 两张热运行中位数 | 3519.78ms | 1284.60ms |
| 1080p 进程峰值内存 | 582.79MiB | 444.51MiB |
| 两张无文字图片误报行数 | 0 | 2 |

耗时包含从文件读图、预处理、检测、裁剪、识别与解码，来自独立 Python 原型；并非原生 Rust worker 或8GB/11代i5实测。峰值为整进程 ru_maxrss，包含 Python、OpenCV、NumPy、运行器、session 元数据检查及缓存，不是权重大小，也不是正式宠物加模型的总内存。首个请求的模型懒加载计入首遍，全部首次/热运行数值保留于原始JSON。没有测完整观察到说话的总延迟，也没有测 CPU 利用率或桌宠帧时。

v5 将 `lI` 认成 `II`；v6 将 `O0 I1 lI` 认成 `00 11II`。两者均读对本轮小数、金额及常规中文；没有据此赋予宠物精确数字处理保证。v6 在[纯几何图形](ocr-cpu-trial-2026-10-11/v6/shapes.png)上输出 `O` 和 `■`，置信度与框保留在原始记录，v5 同图没有输出。默认置信阈值均0.5，本轮没有通过调阈值隐藏误报。

## 字典与坐标核对

两个识别 ONNX 已自带 `character` 元数据，不需要另行联网下载字典。v5 字典18383行，原始字典字符串 SHA-256 `17665d27ed39f0deb82007859992d626d3105d0ee4578c120b7c72138dc04d05`；v6 字典6904行，SHA-256 `34d139222b6e8d84830f57476e39f01e76be3baffde3e9df75a079e251140598`。CTC 在前方增加 blank、后方增加空格，分别与输出18385/6906维匹配。不得将两套字典互换，也不能把类别数量直接当成准确率。

识别输入为动态batch、3×48×动态宽度；检测输入为空间动态尺寸。采用 RapidOCR 默认检测归一化 mean/std=0.5、短边736、框阈值0.5，识别高48、基础宽320、batch6；框排序、裁剪和 CTC 使用固定版本实现。记录了输入/输出维度、模型SHA与字典SHA，后续移植按此做逐阶段对照，不能只对最终字符串“看起来差不多”。

所有含文字样本的输出行数与参考行数一致，检测框均在原图范围内，框中心落在预期文字行范围且顺序正确；这证明本轮单列样本缩放还原和行顺序符合预期，不涵盖多栏、旋转、复杂遮挡或所有DPI设置。已查看12px中文、整页和误报图形原图。

## 复现与证据

脚本：[ocr-trial.py](../../scripts/ai-prototype/ocr-trial.py)。在 Linux 仓库外新建虚拟环境，按依赖锁安装；从[固定来源与哈希](next-ai-integration-2026-10-11/models.json)下载四个 ONNX 到仓库外模型目录。

```bash
python scripts/ai-prototype/ocr-trial.py \
  --models /absolute/path/ocr-models \
  --output /absolute/path/new-v5-output \
  --candidate v5 --threads 2 \
  --font /usr/share/fonts/opentype/noto/NotoSansCJK-Regular.ttc
```

切换 `--candidate v6` 比较tiny；加 `--suite dense` 测整页。使用不同的全新输出目录，脚本拒绝覆盖非空目录。模型校验基于仓库已核验清单；完整环境、字典元数据、真实回复/分数/框、逐次耗时和图片哈希保存如下：

- [稀疏 v5](ocr-cpu-trial-2026-10-11/v5/v5-results.json)、[稀疏 v6](ocr-cpu-trial-2026-10-11/v6/v6-results.json)
- [整页 v5](ocr-cpu-trial-2026-10-11/dense-v5/v5-results.json)、[整页 v6](ocr-cpu-trial-2026-10-11/dense-v6/v6-results.json)
- [证据一致性核对](ocr-cpu-trial-2026-10-11/checks.json)

稀疏轮之后脚本增加dense模式、输出目录/线程校验及改从仓库固定清单读哈希，识别设置和稀疏样本未改变；最终脚本哈希记录在checks.json。
