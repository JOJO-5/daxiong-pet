# 用户确认路线：Qwen3.5 2B 多模态 + 独立 CPU OCR

2026-10-10（北京时间），用户认可按8GB内存、11代i5配置推进Qwen3.5 2B，再补一个OCR。此为产品/开发路线决定，不是假设已通过实际设备测试。此前小样本研究保留，不再因共享云机两核配额的生成耗时排除2B。

## 模型与视觉组件

Qwen3.5 2B架构支持文字和图片，不是Qwen2.5纯文字模型。llama.cpp GGUF路线需要配套视觉组件，不是只有语言GGUF文件就自动能看图：

| 文件 | 字节 | 状态 |
| --- | ---: | --- |
| Qwen3.5-2B-Q4_K_M.gguf | 1,270,808,032 | 已下载、校验并完成纯文字CPU试验 |
| mmproj-Qwen3.5-2B-BF16.gguf | 671,372,416 | 固定元数据；未下载/执行 |
| 两者合计 | 1,942,180,448 | 约1.94GB十进制，只是权重文件，不是安装包或运行内存 |

来源/固定revision/哈希见[候选清单](chat-model-candidates-2026-10-10.json)，开发清单见[default-model.json](../../scripts/ai-prototype/default-model.json)。计划AI完整包包含2B及匹配视觉组件，图片组件按需使用，普通文字聊天不必加载视觉组件；最终还要验证运行器能否按此方式切换和释放。此前0.8B六次图像试验不能当作2B图像验证，2B的图片内存和速度均未知。纯文字进程约2.1GiB的历史峰值也不能当作图片模式内存预算。

8GB/11代i5作为主要原生验收配置；具体i5 SKU、功耗、实际空闲内存影响响应。比较2/4线程、首正文、首句、整段、模型/OCR进程树内存、取消与卸载，保留无AI的拖动/球/盘动画基线。不得按核数直接承诺翻倍，不能把共享云机结果作为该配置的性能结论。

## OCR 实施候选

优先原型：**RapidOCR v3.10.0 + ONNX Runtime CPU + PP-OCRv5 mobile检测/中文识别**。v6 tiny作为体积/性能对照，不仅凭模型表尺寸替换质量更好的路线。所有OCR模型尚未下载或推理；此处确定评测入口，不宣布OCR已经完成。

已实际查询上游v3.10.0发布（2026-10-08），该标签的模型映射包含v5 mobile的明确ONNX来源和声明SHA-256，以及v6 tiny对应ONNX。上游v3.10.0默认配置为**v6 small**，因此试验必须明确指定v5 mobile，不能沿用默认下载并误称测了v5。固定配置/模型路由/框架许可证保存在[来源证据](qwen35-2b-ocr-route-2026-10-10/sources.json)；[OCR候选清单](qwen35-2b-ocr-route-2026-10-10/ocr-candidates.json)保存四个模型的来源和上游声明哈希。声明哈希尚未由实际下载文件验证。

普通屏幕文字先测检测+识别，方向分类先关闭，旋转文字作为另外验证项。必须核对识别字典、ONNX元数据、预处理与框坐标还原。RapidOCR原型使用Python不代表正式包要求用户安装Python；正式Tauri分发需独立打包worker或移植对应处理并使用原生ONNX Runtime，按完整包和原生平台分别验证。框架Apache-2.0许可证已保存；转换模型、字典及ONNX Runtime的再分发许可仍逐项核对。

## 处理路线和下一执行项

1. 普通办公窗口：授权截图→变化检测→OCR有限文字/位置/置信度→2B生成短句。不要求每次观察都跑图片推理，也不要求每次观察都说话。
2. 主人主动问图片、图表或画面关系，或窗口以图片为主：按需将有限图片交给同一2B及匹配视觉组件。OCR只是识字，不负责代替完整画面理解。
3. 默认不让OCR、图片编码和语言生成同时抢满CPU；聊天优先、过期观察跳过，所有任务独立于宠物实时tick。屏幕仍仅短期上下文，不能自动当长期偏好。
4. 下一轮下载并校验选定ONNX/字典，跑中文12/14/16px、英文代码、金额/小数/0与O/I与l、混排/低对比和不含文字图片，测识字误差、整页/文字行耗时、CPU与内存；结合v6 tiny比较，再确定最终OCR组合。
5. 补测2B真实图片协议与配套组件，然后做短句/性格聊天原型和8GB目标设备性能验证。未完成这些步骤前不宣布多模态已接入宠物或8GB性能通过。
